# 지연 입력은 제한된 이력 안에서만 다시 계산

[게임 소개](../../README.md) · [전체 사례](../case-studies.md) · [코드 가이드](../code-guide.md)

**S / 상황**

늦게 도착한 방향 전환으로 이동 경로가 달라집니다. 과거 경로를 바꾸면서 별 수집이나 도착 판정까지 새로 발행하면 게임 결과의 일관성이 깨집니다.

**T / 과제**

일반 이동 구간의 입력은 보정하되, 이미 확정된 판정과 외부 이벤트를 유지해야 했습니다.

**A / 상태 복원과 부작용 발행 경계**

요청 틱은 보관 이력~현재 틱으로 제한해 모든 참가자 입력을 재생합니다. 확정 판정 이전 이력은 폐기합니다.

1. **재계산 대상:** 실제 `State`의 위치·방향과 접촉 ID 집합을 이력으로 바꿉니다. 별도 임시 State는 두지 않습니다.
2. **발행 경계:** 수집·도착·위험 이벤트는 재계산 중 발행하지 않습니다. 외부 수집·이벤트 상태는 변경하지 않아 복원 대상이 아닙니다.
3. **취소 후:** 과거 틱의 새 접촉 시 현재 위치·방향·접촉 ID를 복원하고, 이번 수신 입력 전체를 현재 틱에 적용합니다. 현재 틱 결과만 반환합니다.

이력 상한 **0.2초는 과거 경로 변경과 재계산 범위를 제한하는 설계 정책**이며, 측정으로 도출한 최적값은 아닙니다. [HostMoveAuthority](../../src/Movement/HostMoveAuthority.cs)의 `Step`, `ReplayFrames`에서 처리 순서를 확인할 수 있습니다.

논리 상태와 렌더링 스무딩을 분리해 시각적 보정 오차를 점진적으로 줄이도록 구성했습니다.

**R / 단일 실행의 관측값**

| 구분 | 관측 내용 |
|---|---|
| 조건 | 2026.10.25 / Android 앱 1.8 / SM-A366N / 2인 Map_02 |
| 범위 | 호스트 로그 225.392초 |
| 재계산 표본 | 81건 |
| 되감은 구간 | 4~11틱 |
| 최대 구간 환산 | 약 183ms = 11틱 ÷ 초당 60틱 |
| 접촉 취소 관측 | 0건 |

183ms는 **되감은 시뮬레이션 범위**이며 RTT·연산 시간이 아닙니다. 0.2초 정책과 이 로그의 관측값을 구분합니다.



## 재계산 취소 시 실제 처리 순서

1. Step 시작 시 현재 위치·방향과 접촉 ID 집합을 보관합니다.
2. 요청 적용 틱을 보관 이력~현재 틱으로 제한하고, 같은 참가자의 후속 명령이 앞선 명령보다 과거에 적용되지 않게 합니다.
3. 변경된 구간의 시작 상태를 복원하고 모든 참가자의 명령을 현재까지 재생합니다.
4. 과거 틱에 새 수집·도착·위험 접촉이 생기면 ReplayFrames가 실패를 반환합니다.
5. 이번 수신 입력 전체를 현재 틱으로 옮기고, Step 시작에 보관한 상태와 접촉 ID 집합에서 현재 틱을 다시 계산합니다.
6. 현재 틱의 결과만 호출자에게 돌려줍니다. 확정할 접촉 결과가 있으면 이력을 비워 이후 재계산의 경계로 삼습니다.

### 코드 발췌: 취소 후 현재 틱 적용

[HostMoveAuthority.Step](../../src/Movement/HostMoveAuthority.cs)의 일부이며, 프레임 확보·이력 정리·진단 갱신은 생략했습니다.

```csharp
if (!ReplayFrames(firstChanged, before, overlaps, out var outcome))
{
    // ... currentFrame 확보 및 이력 정리 등 중간 생략
    currentFrame.Commands.AddRange(incoming);
    ReplayFrames(0, presentBefore, presentOverlaps, out outcome);
}
```

과거 구간의 접촉 결과를 외부 이벤트로 발행한 뒤 취소하는 방식 대신, 외부 발행 전의 재계산 단계에서 현재 틱 적용으로 전환했습니다. 0.2초 정책과 183ms 관측값은 별개의 근거로 설명합니다.


## 왜 취소 시 수신 입력 전체를 현재 틱으로 옮겼는가

ReplayFrames는 State뿐 아니라 프레임별 시작 상태와 접촉 ID 이력도 갱신합니다. 과거의 새 접촉으로 중단되면 중간까지 계산된 상태가 남으므로, 그 상태를 기준으로 다음 입력을 처리할 수 없습니다.

문제가 된 입력 하나만 골라 제외하는 대안은 남은 입력이 적용될 과거 프레임과 참가자별 적용 순서를 다시 조합해야 합니다. 현행 정책은 **Step 시작 상태 하나로 되돌린 뒤 이번 수신 배치를 수신 순서 그대로 현재 틱에 재적용**해 복구 기준을 단순하게 유지합니다.

그 대신 같은 배치에 포함된 다른 입력도 과거 시점 보정을 포기합니다. 입력별 최적 보정보다 기존 판정 보호와 명확한 복구 경계를 우선한 정책입니다. 이미 발행한 판정 경계를 넘는 재계산은 허용하지 않습니다.

## 재계산 취소 분기의 실행 검사

[검사 코드: ReplayCancellationCase.cs](../../tests/ReplayCancellationCase.cs)

기존의 단일 실기기 로그에서는 접촉 취소가 관측되지 않았으므로, 별·골·위험 접촉과 두 입력이 함께 수신되는 경우를 별도 .NET 검사에서 구성했습니다. 이는 라이브 통신의 재현 결과가 아닌 **제품 이동 로직의 분기 검사**입니다.

### 조건

- 원점 (0, 0)에서 틱당 0.1만큼 위로 이동해 4틱 후 (0, 0.4)에 도달합니다.
- 참가자 0은 W/S, 참가자 1은 A/D만 담당하도록 검사에서도 키를 나눕니다.
- 5틱 처리 전에 참가자 1의 D 입력이 적용 예정 틱 1로 늦게 도착합니다.
- 재계산 경로의 (0.2, 0)에 새로운 접촉을 두어 과거 틱에서 취소되게 합니다.
- 원래 경로에는 시작부터 겹쳐 있던 별을 둡니다. 실패한 재계산이 겹침 정보를 바꿨더라도 복원 후 이 별을 다시 발행하면 실패입니다.

### 예상 상태와 실제 결과

| 검사 | 예상 결과 | 확인 결과 |
|---|---|---|
| 과거 새 별·골·위험 접촉 | 세 종류 모두 재계산 취소 | 세 종류 모두 취소 플래그 확인 |
| 현재 상태 복원 | 5틱 시작 위치 (0, 0.4), 방향 Up | 위치·방향 일치 |
| 늦은 입력의 현재 틱 적용 | 5틱 종료 (0.1, 0.4), 방향 Right, 적용 틱 5 | 위치·방향·적용 틱 일치 |
| 이벤트·접촉 ID 복원 | 과거 새 접촉 및 이미 겹친 별의 발행 0회 | 모두 0회 |
| 다음 틱 상태 | 6틱 종료 (0.2, 0.4), 새 이벤트 0회 | 위치 일치·발행 0회 |
| 한 배치에 D@1, S@5 수신 | 둘 다 5틱 적용, 수신 순서 D→S, 종료 (0, 0.3)/Down | 적용 틱·순서·위치·방향 일치 |

### 실행 범위

외부 .NET 10 검사 프로젝트가 제품 Domain/Application의 이동 소스를 직접 컴파일하고, 공개한 검사 코드의 Run을 호출했습니다. 공개 사본과 제품 원본의 실행문이 같음을 별도로 비교했습니다. 충돌 조회만 PointMap 대역으로 바꿨으며, Unity·UGS·다중 기기 검증과 구분합니다. 검사 프로젝트와 모든 보조 자료형을 포함한 독립 실행 패키지는 공개 범위에 포함하지 않았습니다.
