# 내 입력은 먼저 반영하고, 최종 상태는 호스트가 확정

[게임 소개](../../README.md) · [전체 사례](../case-studies.md) · [코드 가이드](../code-guide.md)

**S / 상황**

호스트 응답을 기다리면 조작이 늦어지고, 예측 결과만 유지하면 다른 참가자의 입력이 반영된 최종 상태와 어긋날 수 있습니다.

**T / 과제**

오래된 상태와 이미 처리된 명령을 구분해 제거하고, 최신 확정 상태에서 미처리 자기 입력만 다시 적용해야 했습니다.

**A / 식별값의 역할과 처리 순서**

- 호스트는 참가자 ID·담당 키·명령 순서·실행 구간 식별값(Epoch)을 검증해 권한 없는 입력, 중복 입력과 상태 초기화 이전의 지연 입력을 차단합니다.
- `Revision`은 확정 상태의 순서입니다. 더 최신인 상태만 수용합니다.
- `Sequence / Ack`는 입력 순서와 호스트 처리 완료 번호입니다. 거부된 명령도 처리 완료 번호를 기준으로 제거합니다.
- `Epoch`는 실행 구간을 구분합니다. 호스트는 이전 회차 입력을 거부하고, 클라이언트는 회차 변경 시 미처리 입력과 정지 플래그를 초기화합니다.

처리 순서는 **로컬 입력 생성 → 다음 로컬 틱의 예측 → 호스트 검증·확정 → 상태 수신 → Revision 검사 → 확정 상태 저장 → Epoch 확인 → 처리 명령 제거 → 확정 위치·방향에서 미처리 입력 재적용**입니다.

호스트와 클라이언트가 사용하는 [공통 이동 규칙](../../src/Movement/SharedMovementRules.cs)을 분리했습니다. [ClientMovePredictor](../../src/Movement/ClientMovePredictor.cs)의 `ApplyConfirmed`, `TryPredict`와 [HostMoveAuthority](../../src/Movement/HostMoveAuthority.cs)의 `Receive`에서 확인할 수 있습니다.

**R / 예측의 누적 오차와 처리된 자기 입력의 재적용 방지**

매번 확정 상태에서 다시 계산하며 상대 입력은 호스트 상태를 통해 반영합니다. 논리 위치 갱신과 화면 표시 보정을 분리했습니다. 명령 번호로 입력·로컬 적용·호스트 처리·화면 반영 로그를 연결했습니다.



## 코드에서 따라갈 순서

| 단계 | 파일·메서드 | 상태가 바뀌는 지점 |
|---|---|---|
| 명령 생성 | [ClientMovePredictor.TryCreateCommand](../../src/Movement/ClientMovePredictor.cs) | 현재 Epoch와 새 Sequence, 다음 로컬 적용 틱을 보관 |
| 호스트 검증 | [HostMoveAuthority.Receive](../../src/Movement/HostMoveAuthority.cs) | 참가자·담당 키·명령 순서·회차를 확인한 입력만 대기열에 추가 |
| 확정 수신 | `ApplyConfirmed` | 최신 Revision만 반영하고 회차 변경 또는 처리 완료 번호에 따라 대기 명령 정리 |
| 재적용 | `TryPredict` | 마지막 확정 위치·방향부터 미처리 자기 입력을 다시 계산 |
| 공통 계산 | [SharedMovementRules.Advance](../../src/Movement/SharedMovementRules.cs) | 충돌 조회로 허용된 거리만 이동 |

### 식별값을 나눈 이유

확정 상태가 최신인지 판단하는 번호와 한 참가자의 입력 순서를 판단하는 번호는 역할이 다릅니다. Revision으로 상태의 역전을 막고, Sequence/Ack로 처리된 입력의 재적용을 막으며, Epoch로 상태 초기화 이전 입력을 구분했습니다.

### 책임 분리

예측기는 논리 이동을 계산하고 수집·도착 이벤트는 실행하지 않습니다. 화면 보정은 별도 표시 계층이 담당합니다. 공개 코드는 이동 규칙·예측·호스트 확정에 집중하며 RPC와 화면 연결 코드는 생략했습니다.


## 설계 선택과 감수한 비용

| 대안 | 현행 선택 | 선택 이유와 감수한 점 |
|---|---|---|
| 호스트 확정 상태가 올 때까지 입력 표시 대기 | 자기 입력을 다음 로컬 틱에 예측 | 응답 대기를 로컬 반응 경로에서 분리합니다. 대신 확정 상태와 미처리 입력을 보관하고 재계산해야 합니다. |
| 각 기기의 로컬 이동 결과를 최종 결과로 사용 | 호스트가 최종 이동·접촉 판정 | 여러 참가자의 입력을 합치는 기준을 한 곳에 둡니다. 상대 입력이나 지연에 따라 자기 예측이 수정될 수 있습니다. |
| 같은 틱에 도착한 방향을 모두 합산 | 호스트 기록 순서대로 적용하고 마지막 방향으로 한 번 이동 | 한 틱에 이동 방향 하나를 갖는 게임 규칙을 유지하며 입력 수만큼 추가 이동하거나 대각선 이동하지 않습니다. 실제 입력 발생 시각순이나 참가자 간 동일 우선권을 보장하는 규칙은 아닙니다. |

이 표는 현재 코드가 선택한 정책과 대안의 차이를 설명합니다. 대안별 성능을 비교 측정했다는 의미는 아닙니다.

## 입력 시간축과 한도

코드 상단의 긴 설명은 이 문서로 옮겼습니다.

- 입력 관측 틱이 L이면 로컬 적용 틱은 L + 1입니다. 호스트 응답을 기다리려고 로컬 반응을 늦추지 않습니다.
- 호스트 적용 틱은 이력 범위, 판정 경계와 참가자 내 명령 순서에 따라 제한될 수 있습니다.
- 확정 상태는 T틱 처리 직후입니다. 예측은 T의 위치·방향에서 다시 시작합니다.
- 적용 예정 틱이 T 이하인데 아직 미처리인 자기 명령은 첫 재계산 틱 T + 1부터 적용합니다.
- 목표 틱은 서버 틱을 기준으로 추정한 로컬 이동 시계에서 얻으며, maxPredictionTicks보다 앞서 예측하지 않습니다.
- 대기 명령 한도에 도달하면 새 입력을 받지 않고, Halt 이후에는 새 회차의 확정 상태를 받기 전까지 입력·예측을 멈춥니다.
